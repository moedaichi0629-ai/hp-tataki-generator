# Googleマップ店舗情報収集・HP作成プロンプト生成ツール

Googleマップから店舗情報を収集し、HP制作候補の店舗を整理・編集・管理したうえで、RaddyAI・Claude Code・Cursor・Lovable・Boltなどの外部AIツールへ渡す「HP作成用プロンプト」を生成するWebアプリです。

- **第1段階**: 旧バージョンの「HPたたき台自動生成」機能を廃止し、店舗情報の収集・保存・編集・管理に特化した構成へ全面刷新
- **第2段階**: HP作成AIへ渡すための画像情報（Googleマップ写真・アップロード画像・外部URL・SNS投稿メモ）を収集・選択・整理する機能を追加
- **第3段階**: HP制作条件（目的・ターゲット・セクション構成・使用画像・技術条件）を設定し、AIツール別のHP作成用プロンプトを生成する機能を追加（今回）

**このアプリはHP自体・HTML・デザイン・プレビューを一切生成しません。** 生成するのはあくまで「AIツールに渡すための指示文（プロンプト）」で、ユーザーがそれをコピーして外部のAIツールへ貼り付けて使う運用です。

## アプリURL

https://hp-tataki-generator-s74r.vercel.app/

> Google Places API・OpenAI APIの利用料金が発生するため、デモ環境でのAPIキーは常時有効化していない場合があります。また、データベース（Supabase）が未接続の状態ではエラーメッセージが表示されます（下記「セットアップ方法」参照）。

### 第1段階

- 店舗検索（地域×業種の一括検索／GoogleマップURLからの個別登録／店名・住所からの個別検索）
- 店舗情報の保存・編集（基本情報・外部リンク・Googleマップ情報・管理情報）
- 店舗一覧（検索・絞り込み・並び替え・ステータス変更・削除・重複確認）
- サービス・メニュー管理、口コミ表示・強み整理（AI下書き機能つき）、メモ機能
- 店舗ステータス・公式サイト確認状態・情報確認状態の管理、重複店舗の防止
- ダッシュボード、旧バージョンからのデータ移行機能

### 第2段階

- 店舗詳細に「画像管理」タブを追加（Googleマップ写真／アップロード画像／外部画像URL／SNS投稿メモ／使用画像一覧の5セクション構成）
- Google Places APIによるGoogleマップ掲載写真の参照情報取得（最大10枚、実体は保存せず都度取得）
- ブラウザからSupabase Storageへの直接アップロード（複数ファイル対応、進捗表示、破損・重複チェック）
- 外部画像URLの参照登録（SSRF対策つきの到達性・Content-Type確認、ダウンロードはしない）
- SNS投稿URLのメモ管理（自動取得は行わない）
- 画像ごとの画像種別・使用用途（複数選択可）・利用確認ステータス・表示順の管理
- HP制作向け画像準備状況のチェック（枚数集計・警告表示）

### 第3段階（今回追加）

- 店舗詳細に「HP制作条件」「プロンプト」タブを追加
- HP制作条件の設定（HPの目的・制作タイプ・想定ターゲット・伝えたい内容・行動喚起・問い合わせ/予約方法・使用技術・公開方法・対応端末・SEO/アクセシビリティ等・納品形式）
- HPセクション構成の管理（22種類から選択、有効/無効・表示順・見出し・掲載内容・使用画像・CTA・補足指示、上下ボタンでの並び替え）
- 使用する画像をセクションごとに第2段階の画像データと連携して指定
- 使用AIツールの選択（RaddyAI / Claude Code / Cursor / Lovable / Bolt / Replit / ChatGPT / Gemini / その他）とツール別プロンプト生成
- プロンプト生成前の不足情報チェック（必須項目が未入力の場合は生成不可、推奨項目は警告表示）
- 生成したプロンプトの編集・全文コピー・保存・再生成・複製・削除・使用済みフラグ・メモ
- 店舗ごとのプロンプト履歴、および全店舗横断のプロンプト履歴ページ（検索・絞り込み）
- 店舗情報・画像情報が更新された場合の鮮度警告（「最新情報を反映していない可能性があります」）

## 機能一覧

### 店舗検索からプロンプト生成までの流れ

1. 店舗検索（地域×業種一括検索／GoogleマップURL登録／店名・住所検索）で店舗を登録
2. 店舗情報管理（基本情報編集、ステータス管理、重複防止）
3. サービス・メニュー、口コミ・強み整理
4. 画像管理（Googleマップ写真取得、アップロード、外部URL、SNSメモ、利用確認ステータス設定）
5. HP制作条件の入力（目的・ターゲット・セクション構成・使用画像・技術条件）
6. 不足情報チェック→使用AIツールを選んでプロンプト生成
7. プロンプトを編集・コピーして外部AIツールへ貼り付け、履歴として保存

### 店舗の登録方法（GoogleマップURL登録を含む）

1. 地域×業種による一括検索（取得件数・最低評価・最低口コミ数・営業中のみ・公式サイトなし候補のみ・登録済み除外の各フィルタに対応）
2. GoogleマップURLからの個別登録（通常URL・短縮URL `maps.app.goo.gl` に対応。Place IDを直接特定できない場合は店名・座標からText Search / Nearby Searchで候補を検索し、複数候補がある場合は選択可能。SSRF対策あり）
3. 店名・住所からの個別検索

### 店舗情報管理

- 店舗一覧：店舗名・地域・業種・評価・口コミ数・公式サイト確認状態・店舗ステータス・営業対象/対象外・登録日・更新日で絞り込み。6種類の並び替えに対応
- 店舗詳細：7タブ（基本情報／サービス・メニュー／口コミ・強み／画像管理／HP制作条件／プロンプト／メモ・管理情報）
- 店舗ステータス14種類（候補〜成約・見送り・対象外。「プロンプト未作成」「プロンプト作成済み」は本段階から実際に使用）
- 公式サイト確認状態6種類。Googleマップの情報だけで「公式サイトなし」と断定しない設計
- 基本情報は項目ごとに確認状態（未確認/確認済み/要修正/掲載しない）を設定可能
- 重複防止：Place ID完全一致を最優先とし、Place IDが無い場合は店名・住所・電話番号・緯度経度（半径50m以内）で重複候補を検出（自動統合はしない）

### 口コミ・強み整理

- Google Places APIから取得した口コミの表示（帰属表示つき、転載機能なし）
- 店舗の強み（よく評価されている点・雰囲気・接客・差別化ポイント・想定ターゲット等）の手動入力、およびOpenAI APIによる下書き生成（口コミ・店舗情報にない内容は作らない制約つき、AI生成である旨の免責表示つき）

### 画像管理

- **Googleマップ写真**: Place Details APIの`photos`フィールドから最大10枚の写真参照情報を取得し、サーバープロキシ経由で表示（実体は保存しない）
- **アップロード画像**: JPEG/PNG/WebP、1ファイル10MB以下、複数同時アップロード（署名付きURLでブラウザから直接Supabase Storageへ）
- **外部画像URL**: URLを参照情報として保存（ダウンロードしない、SSRF対策つきで到達性確認）
- **SNS投稿メモ**: Instagram/X/Facebookなどの投稿URLをメモとして保存（自動取得は行わない）
- 画像種別・使用用途（複数選択）・利用確認ステータス・表示順の管理、使用画像一覧でのフィルタ・並び替え

### HP制作条件

- 基本設定：HPの目的（複数選択）・制作タイプ・想定ターゲット・伝えたい内容・店舗の強み補足・ユーザーに取ってほしい行動・問い合わせ/予約方法・掲載しない情報・注意事項・自由記述の補足指示
- 技術・公開条件：使用技術・公開方法・対応端末・SEO/アクセシビリティ対応・Googleマップ埋め込み・SNSリンク・フォーム・アニメーション・更新しやすさの希望・外部サービス連携・納品形式
- セクション構成：22種類のセクションから選択し、有効/無効・表示順・見出し・掲載内容・使用画像・CTA・補足指示を設定。業種を問わない初期おすすめセクション（ファーストビュー・店舗紹介・特徴/強み・サービス・営業時間・アクセス・お問い合わせ）をワンクリックで追加可能（あくまで初期候補で、自由に変更・削除できる）

### AIツール別プロンプト

- **RaddyAI向け**: 専門用語を抑え、店舗情報・構成・掲載内容・使用画像の指定を最優先にした構成
- **Claude Code・Cursor向け**: 機能単位で段階的に実装する指示、ファイル構成・データ構造・テスト・ビルド確認・README更新・完了報告までを含む詳細版
- **Lovable・Bolt・Replit向け**: 画面構成・要件中心で、コードの細部には踏み込まない構成
- **ChatGPT・Gemini・その他**: 汎用的な構成案・文章たたき台作成用のプロンプト
- 「その他」を選んだ場合はツール名を自由入力可能

プロンプトは「ルールベースでの構造化生成」を基本とし、店舗名・住所・電話番号・営業時間・サービス・画像指定などの事実情報は必ずコード側で正確に組み立てます。任意でOpenAI APIによる文章整形（言い回しの改善のみ、事実の追加・削除・変更は禁止）を有効にできます。

### 不足情報チェック

プロンプト生成前に、以下を3段階でチェックします。

- **エラー**（生成不可）：店舗名・業種・住所・HPの目的・制作タイプ・想定ターゲット・有効なセクション・ユーザーに取ってほしい行動・問い合わせ/予約方法・使用AIツール
- **警告**（生成可能だが確認推奨）：電話番号・営業時間・サービス情報・店舗の強み・使用画像・メイン画像候補
- **情報**：公式サイトURL・SNS URL・よくある質問セクションなど

必須項目（エラー）が1つでもある場合、生成ボタンは無効化されます。

### プロンプト編集・コピー・保存・履歴

- 生成後の全文編集、全文コピー（コピー成功/失敗をメッセージ表示）
- 再生成（確認ダイアログあり。既存の編集内容を上書きする旨を明示）
- タイトル変更・使用AIツール変更・使用済みフラグ・メモ
- 複製、削除
- 店舗ごとの履歴、および全店舗横断のプロンプト履歴ページ（店舗名・AIツール・種類・作成日・使用済み・鮮度で絞り込み）
- 店舗情報または画像情報が、プロンプト生成後に更新された場合は「店舗情報が更新されています。このプロンプトは最新情報を反映していない可能性があります。」と警告表示

### 第1段階

1. 既存プロジェクト構成の調査
2. 削除対象と残す対象の整理

4. HP生成関連のAPI Route・ライブラリ・型定義・UIの削除
5. 店舗検索APIの拡張、店舗CRUD・重複判定の実装
6. ダッシュボード・店舗一覧・店舗詳細・編集・設定の各画面実装
7. 全API Routeでのエラーハンドリング統一
8. TypeScriptチェック・ESLint・ビルド確認、README更新

### 第2段階

1. 第1段階後のコード構成（店舗詳細タブ構成・DB・Google Places API利用状況・ストレージ有無）を確認
2. 画像データ構造（`store_images` / `store_social_image_references`）を設計し、Supabase Storageバケットとあわせてマイグレーション作成
3. Google Places APIの写真参照取得処理・サーバープロキシ配信を実装
4. 署名付きアップロードURL方式でのブラウザ直アップロードを実装（Vercelのリクエストボディ上限を回避するため）
5. 外部URL確認（SSRF対策）・SNS投稿メモ・画像CRUD・並び替え・一括操作のAPIを実装
6. 画像管理タブのUI（5セクション＋プレビュー＋準備状況パネル）を実装し店舗詳細へ組み込み
7. 店舗削除時のStorageクリーンアップを追加
8. TypeScriptチェック・ESLint・ビルド確認、実際のSupabaseに対するAPI疎通確認、README更新

### 第3段階

1. 第1・2段階後のコード構成（店舗詳細タブ・DB・画像データ）を確認

4. 不足情報チェック関数、プロンプト組み立て関数（安全なMarkdown断片生成→テンプレートへの差し込み）を実装
5. HP制作条件・セクションCRUD APIを実装
6. プロンプト生成・履歴・編集・複製・再生成APIを実装（生成ロジックは「HP初回作成」のみ、他の種類はデータ構造のみ準備）
7. HP制作条件タブ・セクション管理UIを実装
8. プロンプトタブ・プロンプト編集ページを実装
9. 全店舗横断のプロンプト履歴ページ、ナビゲーション追加
10. ダッシュボードにプロンプト関連の集計を追加
11. TypeScriptチェック・ESLint・ビルド確認
12. 実際のSupabaseプロジェクトに対するAPI疎通確認（HP制作条件保存・セクション追加・複数AIツール向けプロンプト生成・事実情報の反映確認・禁止画像の除外確認・再生成・複製・鮮度検知まで確認）
13. README更新

## セットアップ方法

1. 依存パッケージをインストール

   ```
   npm install
   ```

2. `.env.local.example` をコピーして `.env.local` を作成し、APIキー・Supabase接続情報を設定

3. Supabaseプロジェクトを作成し、SQL Editorで `supabase/migrations/0001_init.sql` → `0002_store_images.sql` → `0003_prompts.sql` の順に実行（`0002`はSupabase Storageのバケット`store-images`、`0003`はAIツール別プロンプトテンプレートの初期データも作成します）

4. 開発サーバーを起動

   ```
   npm run dev
   ```

## 環境変数

```
GOOGLE_PLACES_API_KEY=          # Google Places API・Geocoding APIキー
OPENAI_API_KEY=                 # OpenAI APIキー（強み整理の下書き・プロンプト文章整形に使用）
OPENAI_MODEL=gpt-4o-mini
SUPABASE_URL=                   # SupabaseプロジェクトのURL（サーバー専用）
SUPABASE_SERVICE_ROLE_KEY=      # Supabaseのservice_roleキー（サーバー専用・秘密）
NEXT_PUBLIC_SUPABASE_URL=       # SUPABASE_URLと同じ値（ブラウザから直接アップロードするため必要）
NEXT_PUBLIC_SUPABASE_ANON_KEY=  # Supabaseのanon/publishableキー（公開可能な鍵）
```

`SUPABASE_SERVICE_ROLE_KEY`はAPI Routeでのみ使用し、クライアントに送出しません。`NEXT_PUBLIC_`が付く2つは、ブラウザからSupabase Storageへ直接ファイルをアップロードするために必要な、公開しても問題ない鍵です（実際のアップロード先パスは、サーバーが発行する署名付きURLでのみ許可されます）。

## データベース構成

Supabase（Postgres）に以下のテーブルを保持しています。

- `stores` / `store_services` / `store_reviews` / `store_strengths` / `store_notes` / `search_histories`（第1段階）
- `store_images` / `store_social_image_references`（第2段階） + Storageバケット`store-images`
- `website_requirements`（店舗ごとのHP制作条件、1店舗1行） / `website_sections`（セクション構成） / `generated_prompts`（生成したプロンプトの履歴） / `prompt_templates`（AIツール・プロンプト種類ごとのテンプレート。現時点では管理画面はなくSQL Editorでの直接編集を想定）

`generated_prompts`は生成時点の店舗情報・画像情報の更新日時をスナップショットとして保持し、現在値と比較することで鮮度警告を実現しています。プロンプト本文は、店舗データから安全に組み立てたMarkdown断片（`src/lib/promptBuilders/blocks.ts`）を`prompt_templates`のプレースホルダーへ差し込む方式で生成しており、生の店舗データを直接テンプレート文字列へ結合することはありません。

## 画像利用上の注意

各画像には以下の利用確認ステータスを設定できます。

未確認 / 営業提案用のみ / 店舗から使用許可あり / 店舗提供画像 / 自分で用意した画像 / フリー素材 / AI生成画像 / 正式公開使用可能 / 使用不可

このうち「未確認」「営業提案用のみ」「使用不可」の画像は、正式公開用のHP作成プロンプトには含めません（制作タイプが「営業提案用サンプル」の場合のみ「営業提案用のみ」画像を例外的に許可します）。またGoogleマップ写真は、利用確認ステータスに関わらず「店舗提供画像」として扱わない旨をプロンプト内に明記しています。

## Google Maps Platform利用上の注意

- Google Places APIから取得した口コミ・写真には、Googleマップ由来である旨の帰属表示を画面上に維持しています（削除・改変しません）
- 口コミ本文をHP掲載用文章としてそのまま転載する機能は実装していません
- Googleマップ写真の実体（バイナリ）は自前のストレージへ保存せず、表示のたびにGoogle Places APIから取得します（詳細は下記）

### Google Places API写真取得の仕組み

- レガシーPlaces API（`maps.googleapis.com/maps/api/place/*`）のPlace Detailsの`photos`フィールドのみを要求するfield mask（`place_id,photos`）で取得します
- 取得するのは`photo_reference`（写真参照情報）・幅・高さ・投稿者情報のみで、画像の実体は一切ダウンロード・保存しません
- 画面での表示は、サーバー側プロキシ（`GET /api/stores/[id]/images/google-photo`）が都度Google Photo APIを呼び出して配信します
- 「写真情報を取得」ボタンは新規取得・再取得の両方を兼ね、`photo_reference`が期限切れになっていた場合も再取得により最新化されます

### 画像アップロードの仕組み

- Vercelのサーバーレス関数にはリクエストボディに約4.5MBの上限があり、推奨の「10MB以下」をサーバー経由アップロードでは満たせません
- そのため、サーバーはSupabase Storageの署名付きアップロードURLを発行するだけに留め、ブラウザから直接Supabase Storageへアップロードします（サーバーはファイルの実バイトを一切扱いません）
- 破損チェックと画像サイズの取得は、ブラウザの`Image()`デコード（失敗時＝破損とみなす）を利用しています
- アップロード先のバケットには、Supabase側で`file_size_limit`（10MB）と`allowed_mime_types`（JPEG/PNG/WebP）を設定し、ストレージ側でも制限を強制しています

## 工夫した点

- **重複登録の防止**：Place ID完全一致を最優先とし、Place IDが無い場合も店名・住所・電話番号・緯度経度（半径50m）の組み合わせで近似判定を行い、自動統合はせずユーザーに確認を委ねる設計にした
- **SSRF対策の使い分け**：GoogleマップURLの短縮URL展開はGoogle系ドメインへの許可リスト方式、外部画像URLはDNS解決したIPアドレスがプライベート/ループバック帯域でないことを検証する方式と、URLの性質に応じて適切な対策を使い分けている
- **DB未接続時の耐障害性**：Supabase未設定時にAPI Routeが例外を投げても、必ず日本語のJSONエラーを返すよう全ルートでハンドリングを統一し、画面がクラッシュしないようにした
- **AI利用範囲の限定**：OpenAIは「強み整理の下書き」と「プロンプト文章の言い回し整形（事実の変更禁止）」にのみ使用し、事実の捏造を防ぐことを最優先にした。デフォルトはAI整形なしのルールベース生成で、AI整形はオプトイン
- **画像の非保存設計**：Googleマップ写真は参照情報のみ保存しプロキシ配信、外部URL・SNS投稿も参照のみで、実体を持つのはユーザーが明示的にアップロードした画像だけという一貫した方針にした
- **プロンプトの安全な組み立て**：店舗データを直接テンプレート文字列に結合せず、安全なビルダー関数がMarkdown断片を生成し、テンプレートのプレースホルダーへ置換する方式にすることで、事実の正確な反映とテンプレートの将来的な編集可能性を両立した
- **画像の利用制限をプロンプトへ反映**：利用確認ステータスに応じて、正式公開用プロンプトから未確認・使用不可・営業提案用のみの画像を自動的に除外し、除外理由も明記することで、権利関係のトラブルを防ぐ設計にした
- **鮮度検知**：生成時点の店舗・画像の更新日時をスナップショットとして保存し、現在値と比較することで「情報が古い可能性がある」プロンプトを可視化した
- **不足情報チェック**：`imageReadiness.ts`と同じ設計思想で、店舗・HP制作条件・セクション・画像を都度チェックする純粋関数にし、必須項目が揃うまで生成ボタンを無効化する設計にした

## 学んだこと

- 単一ページの生成ツールを、複数テーブルにまたがる管理システムへ移行する際は、削除範囲と残す範囲を先に明文化してから着手すると手戻りが少ない
- 「Googleマップに公式サイトがない＝実在しない」と断定しない設計（確認状態を多段階で持つ）は、営業判断を誤らせないための重要な安全策になる
- サーバーレス環境では、DB未接続などの初期化エラーが同期的にthrowされるケースを想定し、全APIルートで一貫したエラーハンドリングを行う必要がある
- Vercelのようなサーバーレス環境でファイルアップロードを扱う場合、リクエストボディサイズの上限を早い段階で確認しておかないと、後から署名付きURL方式への設計変更が必要になる
- Supabase StorageのAPIゲートウェイは、署名付きアップロードURLへのリクエストであってもプロジェクトのAPIキー（anon/publishable）を要求するため、「サーバーの秘密鍵だけで完結する」という当初の想定が崩れることがある。ライブラリの内部実装（HTTPリクエストの実体）を確認してから設計する重要性を実感した
- AIに「文章生成」を丸ごと任せるのではなく、「事実の組み立てはコード、言い回しの整形だけAI」のように役割を分離すると、事実の正確性を保ったままAIの利便性も活かせる
- テンプレートをプレースホルダー方式にしておくと、見出しの重複のような「テンプレート側と生成関数側の責務の境界」の不整合に気づきやすく、実際のプロンプト出力を目視確認することの重要性を再認識した
